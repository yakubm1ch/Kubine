# Kubine Project Structure

> Version: Engine Core v1

---

# Purpose

This document defines the physical structure of every Kubine project.

Every project based on Kubine should follow the same directory layout.

This guarantees:

* predictability;
* portability;
* maintainability;
* automatic module discovery.

---

# Root Structure

```text
Kubine/

├── docs/
├── public/
├── src/
├── modules/
├── providers/
├── runtime/
├── scripts/
├── .env
├── package.json
└── README.md
```

---

# docs/

Contains all engine documentation.

Never imported into runtime.

Purpose:

* architecture
* specifications
* roadmap
* developer guides

---

# public/

Static public assets.

Examples

* robots.txt
* manifest.json
* default favicon
* placeholder assets

Files here are never generated by Kubine.

---

# src/

Contains Engine source code.

The engine itself lives here.

Example

```text
src/

bootstrap/

core/

services/

stores/

router/

components/

layouts/

utils/

config/
```

The Engine must remain independent from any specific project.

---

# modules/

Contains feature modules.

Example

```text
modules/

blog/

shop/

portfolio/

wiki/

crm/
```

Each module is fully isolated.

Every module contains:

```text
module.json

routes/

components/

stores/

services/

migrations/

admin/

assets/
```

---

# providers/

Contains adapters.

Example

```text
providers/

database/

storage/

authentication/

search/

email/
```

Examples

Supabase

Firebase

PocketBase

Appwrite

PostgreSQL

SQLite

The Runtime loads only one provider implementation for each provider type.

---

# runtime/

Contains Runtime internals.

Example

```text
runtime/

EngineContext

EventBus

ModuleRegistry

MigrationRunner

ConfigurationLoader

ProviderLoader

ThemeLoader

NavigationLoader
```

Projects never access Runtime directly.

---

# scripts/

Automation scripts.

Examples

Database initialization

Migration generation

Provider installation

Project creation

Development tools

---

# Project Assets

Projects never modify Engine assets.

Instead they store references.

Examples

Logos

Hero images

Backgrounds

Icons

Storage providers contain physical files.

---

# Configuration

Configuration is divided into three levels.

Engine

↓

Project

↓

User

Every level overrides the previous one without modifying it.

---

# Module Ownership

Every module owns:

Routes

Stores

Services

Database

Admin pages

Assets

Settings

The Engine owns none of them.

---

# Runtime Ownership

Runtime owns:

Initialization

Discovery

Dependency resolution

Provider loading

Migration execution

Module lifecycle

Event system

Nothing else.

---

# Engine Rule

Kubine source code should never be modified when creating a new project.

Only:

Project configuration

Modules

Content

should change.

---

# Long-Term Goal

A Kubine repository should be capable of generating completely different applications while keeping exactly the same Engine source code.
